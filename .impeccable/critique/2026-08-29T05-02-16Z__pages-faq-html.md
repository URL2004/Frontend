## Design Specificity Verdict

FAQ는 좌측 앱 셸, 옅은 라벤더 배경, 보라색 강조, 880px 읽기 폭을 공유해 현재 로그인 홈페이지와 한 제품처럼 보인다. 도움말 화면이 메인 컴포저보다 조용한 것도 적절하다. 다만 랜딩 FAQ는 흰 카드형 native `details`, 메인 FAQ는 2열 카드, 전용 FAQ는 밑줄형 아코디언으로 세 구현이 공존해 제품 고유성보다 누적된 변형이 더 두드러진다.

자동 탐지는 0건이었지만 HTML 파서 의존성이 없어 정규식 폴백으로 동작했다. 따라서 0건은 정상 판정이 아니라 과소 탐지다. 실제 코드와 브라우저에서는 `aria-expanded`·`aria-controls` 누락, 닫힌 질문 글자 대비 부족, 중복 FAQ 체계가 확인됐다. 오버레이는 브라우저가 가변 스크립트 주입을 지원하지 않아 제공하지 못했다.

## Overall Impression

읽기 리듬은 괜찮고 주장도 비교적 정직하다. 가장 큰 기회는 FAQ를 판매 배너가 붙은 설명 페이지가 아니라, 사용자의 의문을 해소한 직후 가장 낮은 부담의 다음 행동으로 이어지는 신뢰 기반 전환면으로 만드는 것이다.

## What's Working

1. 4개 범주와 점진적으로 펼치는 아코디언이 11개 질문을 무리 없이 나눈다.
2. AI 감지가 작성 주체를 확정하지 않는 참고 결과라는 고지가 서비스 신뢰를 지킨다.
3. 모바일 390px에서 가로 넘침이 없고 질문 행 61px, 문의 CTA 44px로 터치 기본기가 괜찮다.

## Priority Issues

### [P1] 현재 제품과 FAQ의 사실이 어긋남

- **What**: `무료로 사용할 수 있나요?` 답변은 가입 후 충전을 요구하지만 랜딩은 가입 시 무료 10크레딧을 제공한다. 개인정보 답변은 메뉴에서 제거된 `결과 보관함`을 여전히 말한다.
- **Why it matters**: FAQ는 결제 직전 불안을 해소하는 표면이다. 여기서 무료 혜택을 숨기고 없는 메뉴를 안내하면 활성화와 신뢰가 동시에 떨어진다.
- **Fix**: 무료 10크레딧으로 가능한 실제 사용량을 명시하고, `결과 보관함`을 `작업 기록`으로 교체한다. FAQ 데이터·JSON-LD 원천도 동시에 갱신한다.
- **Suggested command**: `$impeccable clarify`

### [P1] 질문 의도와 무관한 강한 하단 오퍼가 도움 흐름을 압도함

- **What**: 차분한 `문의 남기기` 카드 직후 모든 콘텐츠 페이지 공통의 진한 그라데이션 오퍼가 붙는다. 계정 상태에 따라 작업 기록·충전·붙여넣기 등 서로 다른 행동을 제안한다.
- **Why it matters**: 정확도·환불·개인정보를 확인하러 온 사용자가 답을 얻은 순간, 질문과 무관한 판매 압력을 받는다. 도움말의 신뢰와 마지막 인상이 약해진다.
- **Fix**: FAQ에서는 공통 인라인 오퍼를 끄거나 중립적인 과업 선택기로 교체한다. 1:1 문의는 지원용으로 분리하고, 제품 행동은 `AI 감지 시작`과 `원문 다듬기 시작` 두 개만 동등하게 둔다.
- **Suggested command**: `$impeccable clarify`, `$impeccable layout`

### [P1] FAQ가 세 군데에서 서로 다른 구조·문구로 관리됨

- **What**: 랜딩은 5개 native `details`, 메인은 4개 카드, 전용 FAQ는 11개 커스텀 아코디언이다. 전용 FAQ만 별도 데이터와 JSON-LD 일치 테스트를 가진다.
- **Why it matters**: 가격·정확도·환불·보관 정책이 한 군데만 바뀌어도 다른 화면이 뒤처진다. 이미 무료 크레딧과 보관함 안내에서 드리프트가 발생했다.
- **Fix**: 질문·답변·카테고리·CTA 의도를 단일 데이터로 만들고, 랜딩과 메인은 그중 핵심 항목만 참조한다. 시각 표현은 표면에 맞게 달라도 내용 원천은 같아야 한다.
- **Suggested command**: `$impeccable harden`

### [P2] 분류가 사용자의 결정 순서와 맞지 않음

- **What**: `AI 감지 · 정확도` 안에 기본/고급, 원문 보존 다듬기, 휴머나이징 품질이 섞여 있다. 서비스 일반에는 의미 보존 질문이 들어 있다.
- **Why it matters**: 첫 사용자는 감지·다듬기·기본·고급의 관계를 다시 머릿속에서 조립해야 한다.
- **Fix**: `처음 이용`, `AI 감지`, `휴머나이징·다듬기`, `결제·환불`, `개인정보` 순으로 재구성하고 상단에는 4개 이하의 빠른 이동 링크를 둔다.
- **Suggested command**: `$impeccable shape`, `$impeccable layout`

### [P2] 아코디언 상태가 보조기기에 전달되지 않음

- **What**: 버튼은 키보드로 열리지만 `aria-expanded`, `aria-controls`, 답변 ID가 없고 JS는 `.open` 클래스만 토글한다.
- **Why it matters**: 화면 낭독 사용자는 답변이 열렸는지 알기 어렵다.
- **Fix**: 질문과 답변을 ID로 연결하고 상태를 동기화한다. 현재 애니메이션과 `prefers-reduced-motion` 대응은 유지한다.
- **Suggested command**: `$impeccable harden`

### [P2] 닫힌 질문과 내부 용어가 읽기 신뢰를 깎음

- **What**: 닫힌 질문의 `#6c7790`은 옅은 배경에서 약 4.16:1로 일반 텍스트 AA 기준에 못 미친다. `서버 감사`는 사용자가 이해하기 어려운 내부 용어다.
- **Why it matters**: FAQ는 빠른 스캔과 쉬운 이해가 핵심이다.
- **Fix**: 질문을 최소 `#5b6275` 수준으로 진하게 하고, `서버 감사`는 `자동 검증`처럼 결과 중심 언어로 바꾼다.
- **Suggested command**: `$impeccable typeset`, `$impeccable clarify`

## Conversion Direction

FAQ의 일은 판매가 아니라 불확실성을 낮추는 것이다. 결제는 FAQ에서 직접 밀기보다, 가장 낮은 부담의 `AI 감지`로 활성화한 뒤 결과 화면의 기존 `휴머나이징으로 이어서`에서 자연스럽게 발생시키는 편이 낫다.

- 정확도 답변을 열었을 때만: `내 글의 문체 신호 확인하기` / `결과는 참고용이며 실제 작성 주체를 판정하지 않습니다.`
- 의미 보존 답변을 열었을 때만: `원문을 비교하며 다듬기` / `핵심 주장·수치·인용은 제출 전 직접 확인해 주세요.`
- 페이지 끝: `답을 확인한 뒤, 필요한 작업을 선택하세요` + `AI 감지 시작` / `원문 다듬기 시작`
- 공통 문구: `시작 전 예상 크레딧을 확인할 수 있어요.`

답변마다 CTA를 붙이지 않는다. 반복 CTA는 배너 무시와 압박감을 만든다. 정확도와 의미 보존이라는 고의도 질문 두 곳, 그리고 페이지 끝 한 곳이면 충분하다.

## Persona Red Flags

**Jordan — 첫 사용자**: 네 가지 처리 용어를 한 번에 보고도 어느 기능부터 써야 하는지 판단할 짧은 가이드가 없다. 하단 `글 붙여넣기`는 감지인지 다듬기인지 모호하다.

**Riley — 꼼꼼한 검증자**: `정밀 검증`, `서버 감사`의 범위와 한계가 링크 없이 넓은 보장처럼 읽힐 수 있다. 무료 크레딧과 보관함 표현의 불일치를 바로 발견한다.

**Casey — 모바일 사용자**: 행 높이와 넘침은 괜찮지만, 문의 카드와 강한 오퍼가 연속돼 마지막 순간 두 행동이 경쟁한다.

## Minor Observations

- 전용 FAQ 제목이 로컬 `<h2>`이며 `<h1>`이 없다. 앱 셸이 문서 제목을 소유하지 않는다면 `<h1>`이 더 적절하다.
- CSS가 v67 카드형, v68 밑줄형, v69 애니메이션 보정으로 누적되고 전역 `!important`를 다시 덮는다. 현재 화면은 정상이나 유지보수 위험이 있다.
- 11개 문항에서는 검색이 필수는 아니다. 먼저 카테고리 점프와 질문 해시를 제공하고, 문항이 늘어날 때 검색을 추가하는 편이 단순하다.
- 자동 탐지 결과 0건은 파서 부재로 인한 정규식 폴백 결과이므로 품질 보증으로 사용하면 안 된다.

## Questions to Consider

- FAQ의 최종 목표는 결제 유도인가, 사용자가 자신에게 맞는 첫 작업을 고르게 하는 것인가?
- 사용자가 정확도 답변을 읽었다면 결제 페이지보다 실제 문체 신호 확인으로 보내는 편이 더 자연스럽지 않은가?
- 세 FAQ 구현을 유지해야 한다면, 적어도 어떤 데이터와 정책 문구를 반드시 공유해야 하는가?
